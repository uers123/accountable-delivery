# accountable-delivery

一个 Claude Code **metaskill**：强制模型在交付任何输出之前，走完「**自测 → 反思 → 返工 → 达标**」的完整闭环。不测试，不交付；不达标，不提交；不反思，不进步。

> 核心原则：*我对这个交付物负责。*

## 为什么需要这个技能

大语言模型擅长产出自信的输出——却极不擅长承认这些输出可能是错的。未经测试的代码被交付、边界场景被遗漏、「能跑」往往是被声称而不是被验证的。

`accountable-delivery` 把「交付」变成一份**行为契约**。它不要求模型「尽量小心」，而是要求模型必须走完一套不可跳过的结构化流程：测试自己的产出、分析每一次失败的根因、返工直到所有选定的质量门禁通过，并诚实报告置信度。

## 工作流程：五阶段闭环

```
阶段 0  启动声明
   →  阶段 1  需求确认与质量门禁定义
   →  阶段 2  实现与自测（真实运行测试并记录通过/失败）
   →  阶段 3  结构化反思与根因分析        ← 核心
   →  阶段 4  返工与验证（重跑全部测试；仍失败则回到阶段 3）
   →  阶段 5  交付与总结（门禁核验、教训、置信度）
```

**只有所有选定的质量门禁全部通过，闭环才算完成。** 随后模型报告交付了什么、返工了几次、学到了什么，以及——诚实地——它的交付置信度。

## 安装

Claude Code 从 `skills` 目录发现技能。为所有项目安装：

```bash
mkdir -p ~/.claude/skills
git clone https://github.com/uers123/accountable-delivery.git ~/.claude/skills/accountable-delivery
```

若只在单个项目内共享，把目录放在该项目仓库的 `.claude/skills/accountable-delivery/` 下即可。唯一必需的文件是 `SKILL.md`；`references/quality-gates.md` 会在选择质量门禁时被自动读取。

> 不同版本的 Claude Code 对技能发现路径的约定可能略有差异——拿不准时，把目录放进某个 `skills` 目录并确认 Claude 能列出该技能。

## 使用方法

当任务与技能的描述匹配时（开始实现、修复 Bug，或被要求「交付」「完成」某项工作），技能会自动激活。若要强制启用，直接说明即可：

> 「请按照 accountable-delivery 技能交付这个功能。」

之后你会看到：

1. 开工前的**自我问责声明**。
2. 复述后的需求，以及选定的质量门禁与各自的通过标准。
3. **测试记录**——真实的通过/失败结果，不允许虚假通过。
4. 测试失败时的**结构化反思日志**（错误分类、根因分析、学到的教训）。
5. 以显式置信度和「可交付 / 不可交付」结论收尾的**交付总结报告**。

通过修改 `SKILL.md` frontmatter 中 `description` 字段的触发词，可以调整技能的自动激活时机。

## 质量门禁

**硬性门禁——所有任务必须全部通过：**

| 门禁 | 验证内容 |
|------|---------|
| Q1 功能完整性 | 需求中的每个功能点都已实现并有对应测试 |
| Q2 结果正确性 | 输出与预期一致，全部断言通过 |
| Q3 异常处理 | 非法输入不崩溃，错误信息清晰可理解 |
| Q4 无退化 | 已有功能不受影响 |

**建议门禁——按任务类型选用：** Q5 性能基线、Q6 代码可读性、Q7 输入验证、Q8 安全性、Q9 兼容性。`references/quality-gates.md` 定义了每个门禁的通过标准，并给出任务类型 → 门禁组合的映射表（例如 API 开发 → Q1–Q4 + Q6，并建议 Q7/Q8；Bug 修复 → Q2–Q4 + Q6）。

## 错误四分类

测试失败时，模型必须将其归入且仅归入以下四类之一：

- **需求理解错误** —— 做出来的东西和用户要的不一致
- **技术实现错误** —— 目标正确，但实现方式不对
- **边界遗漏** —— 没有考虑到某种输入或场景
- **性能 / 质量不达标** —— 功能对了，但不够好

分类驱动根因分析，让返工修复的是**原因**，而不仅仅是症状。

## 关键规则

1. 不可跳过反思（阶段 3）——不反思就返工是修补，不是改进。
2. 不可虚假通过——测试必须真实运行并验证结果。
3. 教训必须记录——不记录教训等于没有进化。
4. 质量门禁不可妥协——任一门禁未通过就不交付。
5. 诚实报告置信度——没把握就如实说「低」并说明原因。

## 已知局限

- **依赖模型自律。** 闭环由模型自己执行，契约的强度取决于模型遵循指令的能力。请把它当作**行为契约**，而非正确性或安全性的保证。
- **自测的上限取决于测试本身。** 在有真实测试运行器、lint 或 CI 的环境里，让本技能与它们**配合使用**，用外部工具验证模型的声称。
- **会带来额外开销。** 结构化报告会拉长每次任务的流程；对一行就能改完的小事，可以选用更轻量的方式。
- **效果随模型而异。** 较弱的模型可能给出更浅的反思或更不可靠的自测。
